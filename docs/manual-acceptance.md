# Operator release acceptance

Historical controlled end-to-end validation is available in private project evidence. It is not a fresh credential-bound execution of this packaged release. No acceptance deployment is created by release preparation and production is not automatically tested.

1. At a separately authorized time, choose a dedicated test bot and test n8n deployment with an empty or explicitly reviewed synthetic database. Do not replace the production bot webhook. Follow installation.md, n8n-setup.md and telegram-setup.md; retain credentials only in n8n and ignored local configuration.
2. Import the six release exports inactive. Bind every credential and TI-00 reference. Set test operator/bot identities. Check Header Auth, private-chat scope, HTTPS routing and execution-data saving disabled. Publish workflows manually in the documented order, then manually register the test bot webhook.
3. Record a baseline through an authorized read-only database session: processed messages, intakes, work items, interactions, tickets and outbox rows for the test operator. Save only counts/status evidence privately, never payloads or credentials.
4. Manually send exactly one short voice message: "Release acceptance test. The printer at Synthetic Relay Company does not print. Normal priority. I have not supplied an email address." Do not use real customer information.
5. Wait for the missing-email prompt. Reply explicitly to that prompt with `release.acceptance@example.invalid`. If a client or priority decision is requested, reply once with the documented selection. Do not manually force stages or resend uncertain messages.
6. Record the operator-produced n8n execution IDs privately. Inspect TI-01 authentication and authorized enqueue, TI-02 download/transcription/validated extraction, TI-03 resolution and resolved interaction, and TI-04 send receipt. If execution payload storage is disabled, use available execution diagnostics together with persisted stage/checkpoint evidence; do not enable secret-bearing logs just to produce a report.
7. Compare against baseline: exactly one processed voice, one intake, one ticket and one final confirmation; one processed reply where requested; successful download/transcription/extraction/resolution; no duplicate intake-stage or ticket groups; no live or expired work/outbox leases; no uncertain delivery. The missing-email prompt is separate from the final confirmation. Check audio length/hash consistency and absence of sensitive values in logs.
8. On failure, preserve private evidence and stop. Give the workflow engineer the manually produced execution ID; diagnosis and repair follow the inactive/version-fenced procedure. Never automatically retry or reconcile an uncertain send.
9. Keep cleanup and unpublishing manual and separately authorized. Retain only a redacted outcome/count summary for release review. Acceptance is PASS only after every invariant is evidenced; otherwise mark REQUIRES OPERATOR ACTION or FAIL.
